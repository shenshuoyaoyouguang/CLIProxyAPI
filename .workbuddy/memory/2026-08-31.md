## 深度代码审核（用 code-review-and-quality 技能，产出 ponytail-code-review.md）

审自己写的改动。**结论 Approve（附条件）**，发现并修复 1 个 Required 性能缺陷。

### 🔴 已修复：持锁执行磁盘 I/O

`cooldown_state.go` 的 `Save()`：`s.mu.Lock()` 之后才 `legacyCleanup.Do(removeLegacyStateFiles)`，而后者 `WalkDir` 整个目录。因为 dir == authDir，目录里几十上百个凭证文件，**首次 Save 会把 16 并发全部挡住**。

修复：改用 `atomic.Bool` + CAS 并**移到加锁之前**：
```go
if s.legacyCleaned.CompareAndSwap(false, true) { s.removeLegacyStateFiles() }
s.mu.Lock(); defer s.mu.Unlock()
```
**关键：必须用 CAS 而非 sync.Once**。`sync.Once.Do` 会让并发调用者阻塞等待第一个完成——即使移到锁外也只是换个地方阻塞。CAS 让没抢到的直接跳过（清理只删旧 .cds 且跳过共享文件路径，与并发写不冲突）。

### 量化后判定可接受的退化

1. **`peek()` O(1) → O(N)**（auto_refresh_loop 去堆的代价）。调用链：每个 auth 刷新完成 → queueReschedule → wake → applyDirty → resetTimer → peek。实测：N=100/5分钟间隔 ≈ 500ns/s 可忽略；N=1000/5s 极端 ≈ 0.3% CPU。接受，但**记录在案**——auth 上万且间隔很短时要重评。同时 upsert 从 O(log N) → O(1) 部分抵消。
2. **升级后旧冷却状态不迁移**（会重建）。分钟~小时级缓存，可接受，是有意选择不是疏忽。
